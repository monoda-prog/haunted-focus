# Haunted Focus — proposed design

Status: assistant-authored planning draft for human review. Not generated by or evidence of use of Kiro. This document describes a possible design, not an existing implementation.

## Interface

A single primary view places the focus timer and clear start/pause/reset controls beside a haunted-house illustration. Below it, show a conventional task list and daily focus-session count and minutes. A settings control exposes reduced motion and any future optional reminder settings.

Completed focus sessions illuminate windows. Completed tasks replace their decorative ghosts with stars. The readable list and statistics are the source of meaning; the scene is a supplementary visual reward. Reduced-motion mode uses static state changes.

## Proposed responsibilities

- **Timer:** manage focus/break phase and idle/running/paused/completed state, with explicit transition rules.
- **Tasks:** manage task text and completion state, using stable identifiers rather than list position.
- **Focus history:** record each completed focus session once with duration and completion timestamp.
- **Daily summary:** derive statistics from completed session records under an explicitly chosen local-day rule.
- **Scene:** derive window and ghost/star state from existing records rather than maintaining a separate reward counter.
- **Preferences:** manage reduced motion and any optional reminder settings.

No framework, dependency, persistence layer, or notification provider has been selected.

## State and time considerations

Use a deadline-based countdown while running rather than assuming every interval callback fires on time. Specify how pause/resume, reload, background tabs, clock changes, and interrupted sessions behave before coding. Record completion idempotently so repeat callbacks cannot duplicate sessions or rewards.

Decide whether daily statistics attribute a session to its completion day. Define handling of midnight and timezone changes, and display the chosen rule. Decide how window visualization behaves after the illustration's visible windows are filled without capping recorded progress.

## Privacy and accessibility

Prefer a small, local-first initial scope, subject to owner approval. Avoid collecting credentials or unnecessary personal information. If browser storage is selected, document its limitations and clearing behavior rather than promising permanent or synchronized data.

Provide keyboard operation, visible focus, semantic task controls, readable contrast, and non-color status cues. Announce meaningful timer transitions without reading every countdown tick. Honor system reduced motion and the user's explicit setting.

## Planned verification

- Timer transitions, pause/reset behavior, and duplicate completion prevention.
- Task creation, completion reversal, deletion, and repeated actions.
- Daily summaries across midnight and timezone edge cases.
- Background-tab and interrupted-session behavior after policy is decided.
- Keyboard operation, screen-reader labels, non-color states, and reduced motion.
- Storage failure and reload behavior if persistence is implemented.

No tests have been run because application code does not yet exist.
